# 포디엄이 데이터화하는 것 — 전체 구조 요약

> 이 문서는 **외부(클로드 챗 등)에 맥락을 넘기기 위한 요약**이다.
> 작업 규칙·함정은 `CLAUDE.md`에 있고, 이 문서는 "무엇을 어떤 모양으로 모으는가"만 다룬다.
> 기준일 2026-08-19.

## 0. 한 줄 정의

**포디엄**(https://podiumclassical.kr)은 국내 **클래식 음악 분야 채용 공고**를 기관 원문에서
직접 모아 한 곳에 보여주고, 부수적으로 **공공 연습실** 정보를 모으는 정적 사이트다.
거래·매칭·지원 기능은 **의도적으로 없다** — 공개 정보를 모아 보여주고 원문으로 내보내는 것까지가 범위다.

## 1. 인프라 (실측 확인)

| 층 | 실체 |
|---|---|
| 사이트 호스팅 | **GitHub Pages** (`Server: GitHub.com`, IP 185.199.108~111.153, Fastly CDN) |
| 저장소 | `github.com/clddy/classic-mule` — **public** |
| 도메인 | `podiumclassical.kr` (CNAME 파일, 2026-08-02 연결) |
| 동적 API | **Cloudflare Workers** + KV — `podium-feedback.*.workers.dev` (피드백 수신, 대시보드 데이터) |
| 수집 실행 | **로컬 윈도우 PC의 작업 스케줄러** (GitHub Actions는 백업) |

Cloudflare Pages도 Netlify도 아니다. 정적 파일은 전부 GitHub Pages, 서버가 필요한 두 가지
(피드백 수신 · 비공개 방문통계 보관)만 Cloudflare Worker에 있다.

**중요한 제약 두 개가 여기서 나온다.**
1. 저장소가 public이라 `data/` 밑은 전부 인터넷에 공개된다 → 방문 통계·내부 분석은 커밋하지 않는다.
2. 한국 공공기관 사이트가 해외 IP(GitHub Actions)에 **조용히 0건**을 돌려준다 →
   수집 주력은 반드시 국내 PC여야 한다. Actions는 PC가 꺼진 날의 백업일 뿐이다.

## 2. 데이터화하는 네 가지

### (1) 채용 공고 — 주력

**규모:** 현재 게시 28건 / 아카이브 누적 **1,239건** / 소스 87개 / 원문 보관 306건

**3층 구조 (핵심 설계):**

```
원문(raw)  →  전량 누적(archive)  →  게시(official)
data/raw/<id>.json   data/archive.json      data/official.json
페이지 본문+첨부 원문   마감분 포함 전량       살아있는 공고만
불변, 공고당 1회       절대 덮어쓰지 않음      매일 재생성
```

- **raw층이 있어서 추출 규칙을 고치면 과거분까지 소급 적용된다.** 재크롤이 필요 없다.
- **official.json은 스냅샷**이라 마감된 공고가 매일 사라진다. 수요 분석에 쓸 전량은 archive에만 있다.

**공고 한 건의 필드 (29개):**

| 그룹 | 필드 |
|---|---|
| 식별 | `id` `source` `channel` `layer` `firstSeen` `extVer` |
| 내용 | `title` `org` `url` `officialUrl` `date` `contact` |
| 분류 | `tier`(직무군) `kind`(직종) `inst`/`instDetails`(악기) `subject`(전공) `region` |
| 조건 | `certReq`(교원자격) `degreeReq` `careerReq` `ageGroup` `personnel` `workHours` `obri` |
| 기한 | `deadline` `deadlineFrom` `isNew` `nonMusic` |

**분류 체계 (아카이브 1,239건 분포):**
- `tier` 직무군 14종 — 연주 752, 교육·취미 196, 교육·대학 69 …
- `kind` 직종 10종 — 반주 563, 강사 223, 단원 108, 교수 62, 지휘 …
- `region` **16개 시도** — 2026-07-01 전남광주통합특별시 출범 반영(`광주·전남`으로 표기)
- `source` 51종 — cjob.co.kr(기독정보넷) 716, goe.go.kr 99, hibrain 78, work.sen.go.kr 72 …

**수집 판정 기준 — "그 글이 거기서 태어났는가?"**
게시자가 직접 올리는 최초 게시처면 수집하고, 다른 데서 긁어온 집계 포털이면
정찰용(원문 링크 해석·연락처 추출)으로만 쓰고 링크를 그쪽으로 내보내지 않는다.

**범위 경계:** 국악은 자매 사이트(풍류)로 분리. 실용음악·무용 제외.
판정 기준 하나 — "클래식 음악 전공자의 기술이 그 자리에서 직접 쓰이는가."
애매한 건은 `docs/scope-decisions.md`에 한 줄씩 이력으로 쌓는다.

**품질 검증 4단:** 추출 → 모양검사 → QC → **L4 상식검증**(LLM이 문맥 모순 판정).
L4는 판정만 하고 고치지도 숨기지도 않는다 — 검증기가 오염원이 되는 게 최악이라서.

### (2) 공공 연습실

**규모:** 약 200곳 (시드 62 + 공유누리 125 + 서울 예약시스템 5 + 즉시예약 8 + 공공 3)

개별 시설을 쫓지 않고 **채널로 수렴**한다 — 행안부 공유누리(eshare.go.kr)가 전국 공공자원을
통합해 두었으므로 그 지도검색 API를 훑는다. 항목마다 지자체 원문 예약처 딥링크가 있어
"링크만 걸고 중계하지 않는다"는 원칙과 맞는다.

수집 항목: 시설명·지역·좌표·요금 구분·방 개수·대여 방식·연주 허용 여부·비치 악기·원문 예약 URL.
(타악·금관 허용 여부와 마림바·팀파니 비치 여부는 확인된 페인포인트라 별도 필드로 둔다)

### (3) 기관 명부 — 수요의 모집단

- `crawler/institutions.csv` — **666행**. 기관명·카테고리·지역·홈페이지·채용게시판 URL·파서 상태
- `data/generic_sources.json` — 자동 발견된 게시판 **48개** (id·기관명·지역·board_url·JS 필요 여부·샘플)
- `data/coverage_report.json` — 명부 대비 **수집 공백**(어느 기관을 아직 못 긁는가)

이 층의 목적: "공고가 안 뜨는 게 진짜 없어서인가, 우리가 못 긁어서인가"를 구분하는 것.

### (4) 방문·검색 — 사이트 자신에 대한 데이터

**공개 저장소에 커밋하지 않는다**(.gitignore). Cloudflare Worker KV로 올려 열쇠로만 본다.

| 파일 | 무엇 | 출처 |
|---|---|---|
| `data/traffic.json` | 방문자가 **들어온 뒤** | GA4 Data API |
| `data/search.json` | 검색결과에 **뜨기 전** (노출·순위·검색어) | Search Console API |

**traffic.json이 담는 축:** 일별 totals · 이벤트별 횟수 · 페이지별 PV/체류 ·
유입경로 · 방문자(도시×기기×OS×브라우저×신규재방문) · 시각별[세션,참여세션] ·
**공고별 열람수** · **필터 조합별 결과 건수** · 열린 공고의 성격(직종·마감임박도·이동처)

**계측 이벤트:** `job_view` `job_outbound` `contact_click` `filter_use` `filter_empty`
`space_view` `space_filter` `practice_outbound` `tg_subscribe_click`
+ GA4 맞춤측정기준 **42개**(job_id·job_inst·f_insts·f_results 등)

**설계 원칙 두 개:**
- **필터 신호가 가장 귀하다.** 공급(공고)은 크롤로 다 알지만 **수요**(사람들이 뭘 찾는가)는
  여기에만 찍힌다. 그래서 축을 쪼개 세지 않고 **조합+결과건수를 한 줄로** 받는다 —
  "지휘를 켰더니 1건"이라는 교차는 축을 나누는 순간 사라진다.
- **봇을 이름으로 걸러내지 않는다.** GA4의 참여세션(engagedSessions) 정의를 그대로 쓴다.
  자동 접속은 참여세션이 0이라 저절로 갈리고, 새 봇이 와도 규칙을 고칠 필요가 없다.

## 3. 파이프라인 (매일 자동)

```
18:00  PodiumCrawler    크롤 → 분류·추출 → archive 병합 → 정적 상세페이지 생성
                        → 연습실 수집 → 구글 색인 통보 → 방문·검색 수집
                        → git commit + push (GitHub Pages 자동 배포)
19:10  PodiumAlert      새 공고 → 텔레그램 구독자에게 (파트×지역 필터)
21:30  PodiumHealth     배포 점검 · 소스별 수집량 baseline 비교 · L4 상식검증
                        → 이상이 있을 때만 텔레그램
```

**헬스체크의 핵심은 baseline 비교다.** 평소 10건 나오던 기관이 오늘 0건이면 공고가 없는 게
아니라 파서가 깨진 것이다. **FAIL 없이 조용히 0건이 되는 게 제일 위험하다.**

## 5. 지금의 한계 (솔직하게)

- **트래픽이 아주 작다.** 순 방문자 10명 안팎, 구글 검색 유입 6명, 재방문자 4~5명.
- **상세 페이지가 아직 구글에 색인되지 않았다.** 28개 전부 "URL is unknown to Google" 상태.
  도메인 연결이 8월 2일이라 새 사이트인 탓이 크고, 사이트맵은 2026-08-19에야 제출했다.
- **본문 추출 품질이 고르지 않다.** 28건 중 8건은 개인정보 약관이 설명으로 들어가 있고,
  6건은 본문이 비어 제목으로 대체되며, 4건은 다른 공고 제목이 섞여 있다.
- **재방문 장치가 작동하지 않는다.** 텔레그램 알림봇을 만들어 뒀으나 13일간 구독 클릭 0회.
- 아트인포·아트모아는 활성 소스지만 "집계 포털 미러링 금지" 원칙과 긴장 관계 —
  원천 기관 직접 파싱으로의 전환이 예정된 별도 작업이다.

## 6. 만들지 않기로 한 것 (되풀이 방지)

프리랜서 객원·대타 **매칭**은 공략 불가로 결론냈다(2026-07 재정립).
구직 게시판·급구·긴급 매칭·'지원하기'류 거래 기능은 다시 만들지 않는다.
판단 기준 한 줄: **"지인 소개를 대체하려 하는가 → 제거 / 공개 정보를 모아 보여주는가 → 유지."**

궁극 방향은 매칭이 아니라 **발견형 프로필 디렉토리**(싸이월드형)다.
